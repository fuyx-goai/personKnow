## 问题明细

### 🔴 严重问题

#### 问题 S-1：我的空间两个原型页签未形成可验收需求

- **位置**：`PRD.draft.md §5.6`、`tech-plan.draft.md §4`
- **描述**：Figma“我的空间”明确包含“容量与用量 / RAG 检索微调 / 账号与安全”三个页签，当前设计只完整定义了容量与用量。
- **影响**：若直接实施，“RAG 检索微调”和“账号与安全”只能继续做占位入口，不符合“严格按照原型”和“全栈完整版本”。
- **建议方案A（推荐）**：实现两个页签的基础完整能力。RAG 页签支持知识库级 `chunk_size`、`chunk_overlap`、`top_k`、`similarity_threshold`，修改切块参数后提示并创建重新索引任务；账号安全页签支持查看当前设备会话、退出单个设备、退出全部设备和同步微信昵称头像。
- **建议方案B**：页签只展示系统固定参数与当前登录设备，不允许修改。实施更快，但功能完整性较弱。
- **用户决策**：接受方案A。依据用户再次强调“严格按照原型”并明确要求进入开发，三个页签均实现真实能力。

### 🟡 建议问题

#### 问题 W-1：公开知识库如何被其他用户发现尚未定义

- **位置**：`PRD.draft.md §5.2`、`tech-plan.draft.md §5`
- **描述**：权限与公开列表 API 已定义，但原型知识库页主要展示当前用户的四类库，没有单独的公开广场。
- **影响**：客户端可能各自采用不同入口，造成 Web 与小程序行为不一致。
- **建议方案A（推荐）**：在原型“全部”筛选结果中先展示“我的知识库”，再展示“公开知识库”；公开卡片沿用相同样式，增加所有者与“只读”标识，不新增底部导航或独立页面。
- **建议方案B**：在顶部筛选中增加“我的 / 公开”切换。更清楚，但对原型视觉改动更明显。
- **用户决策**：接受方案A。保持原型卡片与导航结构，不增加独立页面。

### 🟢 优化建议

#### 优化 O-1：文档内容版本是否提供用户回滚入口

- **位置**：`database.draft.md §3.9`、`tech-plan.draft.md §4.4`
- **描述**：后端保存最近内容版本，但原型没有版本历史或恢复入口。
- **建议方案A（推荐）**：MVP 仅内部保留最近 10 个版本，用于失败恢复和审计，不新增用户界面；后续版本再开放回滚。
- **建议方案B**：本期增加版本历史与恢复接口，并在在线编辑弹层增加入口。能力更完整，但超出原型现有交互。
- **用户决策**：接受方案A。首版仅后台保留版本，不扩展原型外页面。
